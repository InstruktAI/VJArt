# VJ Art Operator Guide

## Architecture Overview

VJ Art has two rendering surfaces driven by a shared engine and type system but running **independent playback pipelines**:

```
                      ┌──────────────────────────────────────────┐
                      │           BRIDGE (Node.js :3000)         │
                      │                                          │
                      │  Sequencer ──► FlowResolver ──► Engine   │
                      │       │                          │       │
                      │       │         SessionManager   │       │
                      │       │         (disk persist)   │       │
                      │       │                        TUI ──► Terminal
                      └───────┼──────────────────────────────────┘
                              │ WebSocket + REST
                              │
                      ┌───────┼──────────────────────────────────┐
                      │       ▼       WEB CLIENT (React)         │
                      │                                          │
                      │  FlowComposer ──► Local Sequencer        │
                      │       │               │                  │
                      │  MoodConductor    FlowResolver           │
                      │       │               │                  │
                      │  OverlaySequencer  Engine ──► ThreeRenderer
                      └──────────────────────────────────────────┘
```

**Bridge** — server process. Runs its own `Sequencer` + `VJEngine`, renders to terminal (TUI). Persists sessions to disk. Exposes REST + WebSocket API for external control.

**Web Client** — browser app. Runs its own `FlowComposer` + `MoodConductor` + `Sequencer` + `VJEngine`, renders via Three.js WebGL. Generates content autonomously; does not mirror bridge playback in real time.

Both share the `@vj-art/engine` package: same generators, same flow system, same type schema. Content pushed to the bridge (via REST/WS) plays on the TUI. Content generated by the web client's composer plays on the WebGL canvas.


## Two Channels

### Primary Channel
The main pattern layer. Driven by `FlowSegment` sequences resolved per-frame into `WorkloadSegment` states. Controls:
- Generator selection and blending (20 families)
- All continuous parameters (speed, chaos, warp, spin, drift, hue, etc.)
- Transforms (scale, rotation, pan, mirror, kaleidoscope)
- Post-processing (blur, feedback, scanlines, pixelate, strobe, glitch)
- Color controls (brightness, contrast, saturation, hue rotation, color cycling)
- Per-cell HSV coloring (hueShift, hueRange, hueSpeed, sat, val, charGamma)

### Overlay Channel
Composited on top of the primary channel. Independent state with blend controls. Used for:
- UI elements (banners, frames, symbols, text)
- Ingested image assets (drag-and-drop)
- Persistent interface layers
- Informational displays

Overlay structure:
```typescript
{
  state: State,           // Same schema as primary — generators, UI sprites, etc.
  blend: {
    opacity: 0-1,
    mode: 'over' | 'blend' | 'multiply' | 'screen' | 'add' | 'absorb',
    fade_in: seconds,
    fade_out: seconds,
  }
}
```

## Continuous Parameters

Every parameter can be a static value or a **flow** — a journey from one value to another with easing.

```typescript
// Static
{ chaos: 0.05 }

// Flow with easing
{ chaos: { from: 0.02, to: 0.12, ease: 'easeInOut' } }

// Flow inheriting start from previous segment's end state
{ chaos: { to: 0.12, ease: 'easeOut' } }
```

Easings: `linear`, `easeIn`, `easeOut`, `easeInOut`

Each mood also defines HSV color ranges appropriate to its character. Calm has narrow hue range and slow hue speed; Party and Storm span the full hue circle with fast rotation.

### Mood Transitions

The `MoodConductor` smoothly blends between moods over N segments (default: 5). During transition, parameter ranges are linearly interpolated, and generator probabilities are weighted between source and target moods.

### Custom Moods

Moods can be uploaded from client-side IndexedDB. A `MoodProfile` defines:
- Generator pool with probabilities
- Parameter ranges with max deltas (how far params can jump per segment)
- Duration range, easing set, palette pool
- Optional: mirror types, kaleidoscope values, invert probability


## Programming Sequences

### FlowSegment Structure

A sequence is an array of `FlowSegment` objects. Each segment defines a duration and a set of parameter flows:

```typescript
const segment: FlowSegment = {
  duration: 12,  // seconds
  flows: {
    generator: 'tide',
    weight: { to: 0.7, ease: 'easeIn' },
    speed: { from: 0.5, to: 1.5, ease: 'easeInOut' },
    chaos: 0.02,
    hueShift: { to: 0.6, ease: 'linear' },
    hueRange: 1.2,
    hueSpeed: 0.05,
    sat: 0.9,
    val: 0.85,
    feedback: { from: 0.3, to: 0.6, ease: 'easeOut' },
    feedbackDecay: 0.9,
    mirror: 'horizontal',
    palette: ['#0a1628', '#1a2f4a', '#2d4a6f'],
  }
}
```

### Continuity Between Segments

The `FlowResolver` tracks end-state. When a flow omits `from`, it inherits the previous segment's end value. This creates smooth journeys across segment boundaries without hard cuts.

### Multi-Generator Segments

For mixing multiple generators in one segment:

```typescript
{
  duration: 10,
  flows: {
    generators: [
      { id: 'tide-3', weight: { from: 0.8, to: 0.3 }, speed: 1.2, warp: 0.6 },
      { id: 'nebula-1', weight: { from: 0.2, to: 0.7 }, speed: 0.8, drift: 0.4 },
    ],
    feedback: 0.5,
    hueSpeed: 0.08,
  }
}
```

Generators cross-fade by weight. Each generator has independent per-cell color params.

### Pushing Sequences

**To Bridge (REST):**
```
POST /workload
{ "segments": [ FlowSegment, ... ] }
```

**To Bridge (WebSocket):**
```
{ "type": "FLOW_APPEND", "data": { "segments": [ ... ] } }
```

**Client composer auto-generates** when the sequencer runs low (< 2 segments remaining).


## Session Management

### Creating Sessions

```
POST /session/start
→ { id, createdAt }
```

A session groups flow segments under a timestamped ID. Sessions persist to disk at `sessions/YYYY-MM-DD/session-{timestamp}.json`.

### Appending to Sessions

```
POST /session/append
{ "segments": [ FlowSegment, ... ] }
```

Segments are appended to the active session on the bridge and broadcast to connected clients.

### Listing and Loading

```
GET /session/list          → All stored sessions
GET /session/:id           → Specific session
POST /session/resume       → Resume latest or by ID
```

When a session is loaded, the bridge sequencer resets and begins playing from the start. The client receives a `SESSION_LOAD` WebSocket message.

### Persistence Model

Bridge persists to disk. Client has ephemeral localStorage backup (30-second TTL for page reload recovery). The vision: client mirrors the server's session library so users can browse and replay any stored sequence.

### Persistent Interface Layers

Overlays can serve as persistent UI — status displays, labels, decorative frames. Since overlays have their own `State` (including full `field_program`), an overlay can run its own generator pattern behind the UI sprites, creating a layered visual.

### Interface Rotation

Store multiple overlay states as a sequence. Toggle through them to cycle interface variations:

```typescript
const interfaces: Overlay[] = [
  // State 1: Minimal — just corner markers
  { state: { field_program: { generators: [] }, ui: [corners] }, blend: { opacity: 0.3, mode: 'over' } },
  // State 2: Info — corners + status bar
  { state: { field_program: { generators: [] }, ui: [corners, statusBar] }, blend: { opacity: 0.5, mode: 'over' } },
  // State 3: Full — corners + status + banner
  { state: { field_program: { generators: [] }, ui: [corners, statusBar, banner] }, blend: { opacity: 0.7, mode: 'screen' } },
]
```

Each toggle steps through the array. The overlay channel fades between states using blend controls.

## Creative Workflows

### Workflow: Curated Set

1. Create a session: `POST /session/start`
2. Compose segments with intentional arcs (build-up → peak → cool-down)
3. Push sequences: `POST /session/append`
4. Bridge plays them on TUI; web client can load and replay from session library
5. Store the session for future shows

### Workflow: Mood-Driven Autopilot

The web client's `FlowComposer` generates infinite content within mood boundaries. The `MoodConductor` transitions between moods. No manual sequencing needed — just set the mood and let it evolve.

To change mood programmatically:
```typescript
conductor.setMood('storm')  // Smooth transition over 5 segments
```

### Workflow: Live Mixing

Combine autopilot with manual overrides:
- Keyboard controls for real-time parameter tweaks
- Tap tempo syncs generator pulsing to music
- Mic input for automatic beat detection
- Scrub/pause/speed for timeline control

### Workflow: Overlay Storytelling

Program a sequence of overlay states that tell a visual story:
1. Start with minimal (scatter dots)
2. Build to banner reveal (VJ ART)
3. Add frame elements
4. Peak with full UI + symbols
5. Dissolve back to clean canvas

Each overlay transition uses fade_in/fade_out for smooth morphing.

### Workflow: Variant Exploration

Browse the 100 named variants to find starting points:

Use variant params as starting points for sequences, then customize flows on top.


## Invariants and Safety

The composer enforces hard invariants to prevent visual breakdown:

- `chaos * updateRate < 1.5` — prevents mutation overload
- `feedback > 0.4` → `chaos < 0.1` — feedback needs stability
- `weight < 0.3` → `chaos < 0.05` — faint patterns need calm
- `kaleidoscope > 0` → `chaos < 0.1` — symmetry needs precision
- `chaos > 0.15` → `duration < 8s` — high chaos segments stay short
- `warp > 1.5` → `chaos < 0.05` — high distortion is already complex
- `spin > 1.5` → `warp < 1.0` — prevent compound visual noise

Soft couplings nudge related parameters:
- `weight up` → `chaos down` (30%)
- `feedback up` → `feedbackDecay up` (50%)
- `speed up` → `blur up` (20%)
- `warp up` → `noise down` (20%)


## Build Plan: The Living Archive

What follows is the concrete blueprint for evolving VJ Art from a real-time VJ engine into a creative platform with memory, taste, and an ever-growing library of visual moments.

---

### Phase 1: State Integrity — The Composer Tells the Truth

**Problem:** The composer only emits params that the current mood defines ranges for. Missing params fall through to engine defaults. The FlowResolver tracks end-state only for params that appeared in a flow. The engine has no memory — it reads what the workload says, and if the workload says nothing, it uses a hardcoded constant. The entire state inheritance chain is broken for params the mood doesn't cover.

**Fix:** The composer maintains a **complete state record** — every continuous param has a known current value at all times. When the mood doesn't define a range for a param, the composer holds the current value (it doesn't drop it). Every FlowSegment emitted is **fully specified**: every param has an explicit `from` (baked from current state) and `to`. No segment depends on the FlowResolver's endState memory for correctness — it is self-contained.

**What changes:**
- `FlowComposer` initializes full state with baseline values for all `CONTINUOUS_KEYS` on construction
- `next()` emits all params, not just the ones the mood ranges. Params outside the mood's scope hold their current value
- Every flow has explicit `from` baked from `this.state[key]` — no more implicit inheritance
- The FlowResolver's endState becomes a convenience for live playback, not a correctness requirement

**Why this matters:** This is the foundation for the living archive. Self-contained segments are only possible if the composer produces them. Everything below depends on this.

---

### Phase 2: Richer Variation — The Composer Surprises

**Problem:** The `pickNext` method is a random walk with tiny maxDelta steps. It converges to the center of the range within a few segments and stays there. Generator selection holds 70% of the time. Mood transitions wait 30-180 seconds. The result: visual mediocrity. The system has 20 generator families, 100 named variants, 30+ continuous params, and 9 moods — but the output looks like one pattern barely changing.

**Fix:**

**Exploration jumps.** 20% of the time, instead of walking from current, pick a fresh value from the full mood range. This breaks the random walk's convergence and ensures the full range gets explored.

**Generator diversity.** Increase reroll probability to 50%. When rerolling, exclude the current generator — force actual change. Use the mood's full generator pool.

**Faster mood cycling.** Initial phrase duration 15-60s instead of 30-180s. The operator can experience multiple moods in the first minutes.

**Shorter initial segments.** Start with a more dynamic mood (Drift or Pulse) instead of Calm. First segments should demonstrate range, not serenity.

**What changes:**
- `pickNext()` gains a 20% chance of `rand(range[0], range[1])` instead of the constrained walk
- Generator reroll probability: 30% → 50%, with current-generator exclusion
- `MoodConductor` phrase duration: 15-60s
- Default starting mood: Drift (more movement than Calm, but not aggressive)

---

### Phase 3: The Archive — Every Segment Stored

**Problem:** Segments play and vanish. The sequencer is an infinite stream with no memory. Sessions on the bridge store raw FlowSegments, but the web client stores nothing.

**Fix:** Every segment that plays — whether from the autopilot composer or from an operator push — is stored in the active session. The session lives on the bridge (disk) and is mirrored to the client (IndexedDB). Every stored segment is a **fully resolved, independently playable atom** with metadata.

**Stored segment schema:**
```typescript
interface ArchivedSegment {
  // Playback unit (self-contained FlowSegment with explicit from/to)
  duration: number
  flows: FlowParams  // all params explicit, all flows have from+to

  // Metadata
  timestamp: number
  session_id: string
  source: 'autopilot' | 'operator'
  mood_id?: string
  generator_id: string
  rating?: number       // -1 (skip), 0 (neutral), 1 (keep)
  tags?: string[]
}
```

**What changes:**
- New `SegmentArchive` class in engine — append-only log with metadata
- Composer's `next()` return value is intercepted, archived, then forwarded to sequencer
- Bridge session storage updated to use `ArchivedSegment`
- Client mirrors session archive via WebSocket sync
- New WebSocket message: `SEGMENT_ARCHIVE` — bridge broadcasts each archived segment to clients

**Data flow:**
```
Composer.next() → ArchivedSegment → Sequencer (play) + Archive (store) + Bridge (sync)
```

---

### Phase 4: The Mirror — Client and Bridge in Sync

**Problem:** Client and bridge run independent pipelines. The bridge doesn't know what the client's composer is generating. The client doesn't replay what the bridge stores. There's no shared truth.

**Fix:** The client becomes the **source of truth for content generation**. Every segment the client's composer produces is sent to the bridge for storage and TUI playback. The bridge becomes the persistence layer and secondary renderer, not an independent content source.

**Architecture shift:**
```
Client Composer → FlowSegment → Local Sequencer (WebGL)
                              → WebSocket → Bridge Sequencer (TUI) + SessionManager (disk)
```

**What changes:**
- Client sends `SEGMENT_EMIT` messages to bridge for every composed segment
- Bridge sequencer receives and plays client-generated segments instead of running its own composer
- Bridge SessionManager archives every received segment
- On client reconnect, bridge sends full session state for catchup
- Both renderers show the same content (with rendering differences — TUI vs WebGL)

**Operator pushes flow through the client:**
- Operator sends intent to bridge via REST
- Bridge forwards to client via WebSocket
- Client applies (replacing autopilot), archives, and mirrors back to bridge
- Single path, single truth, two renderers

---

### Phase 5: Operator Control — Deltas on Current State

**Problem:** When an operator (AI or human) wants to steer the visuals, they need to push a FlowSegment that flows smoothly from wherever the system currently is. The operator shouldn't have to know the current values of all 30+ params — they should specify only what they want to change.

**Fix:** New endpoint and message type for **operator deltas**. The operator specifies only the params they want to drive. The system resolves the delta against current state, produces a complete FlowSegment with explicit `from` (current) and `to` (operator intent), archives it, and plays it.

**Operator delta schema:**
```typescript
interface OperatorDelta {
  // Only specify what you want to change
  generator?: string
  duration?: number
  ease?: Easing
  params?: Partial<Record<ContinuousKey, number>>  // target values
  mirror?: string
  kaleidoscope?: number
  invert?: boolean
  palette?: string[]
}
```

**What changes:**
- New `POST /operator/push` endpoint on bridge
- Bridge resolves delta against current state → complete FlowSegment
- Segment is marked `source: 'operator'` in archive
- Operator push pauses autopilot; autopilot resumes from operator's end state when push sequence completes

**Natural language path:**
```
"Take me to deep ocean" → promptToVariant('deep ocean') → 'tide-2'
→ OperatorDelta { generator: 'tide-2', params: { feedback: 0.6, hueSpeed: 0.04 } }
→ Resolved FlowSegment with smooth transition from current state
```

---

### Phase 6: Session Library — Browse, Replay, Curate

**Problem:** Sessions are stored but there's no interface to browse, replay, or curate them.

**Fix:** Bridge exposes rich session browsing APIs. Client gets a session library UI.

**New API endpoints:**
```
GET  /archive/sessions                → All sessions with metadata
GET  /archive/sessions/:id/segments   → All segments in a session
GET  /archive/search                  → Search by generator, mood, param ranges, rating
POST /archive/segments/:id/rate       → Rate a segment (-1, 0, 1)
POST /archive/segments/:id/tag        → Tag a segment
POST /archive/compile                 → Compile a set from segment IDs
```

**Session library UI (web client):**
- Sidebar or modal showing stored sessions by date
- Session preview: mood distribution, generator distribution, duration, segment count
- Click to load and replay any session
- Segment-level browsing within a session
- Star/skip ratings from keyboard during playback (`S` = rotates favorite: starred > neutral (default) > dislike)
- Tags assignable per segment

**Compile workflow:**
1. Search archive: "show me tide segments with feedback > 0.5"
2. Audition results (play individual segments)
3. Select favorites
4. "Compile set" — system generates bridge segments between picks
5. Result: a new session with smooth transitions between curated moments

### Phase 7: Overlay Sequences — The Interface as Content

**Problem:** Overlays are either pushed via REST (manual) or rotated by the OverlaySequencer (random). There's no way to program intentional overlay sequences, store them, or cycle through designed interface states.

**Fix:** Overlay sequences become first-class stored content, parallel to the primary channel.

**Overlay sequence schema:**
```typescript
interface OverlaySequence {
  id: string
  name: string
  states: {
    overlay: Overlay
    duration: number
    transition: { fade_in: number, fade_out: number }
  }[]
  loop: boolean
}
```

**What changes:**
- `OverlaySequencer` upgraded to play stored `OverlaySequence` objects, not just random presets
- New `POST /overlay/sequence` endpoint to push a named sequence
- Overlay sequences stored alongside sessions in the archive
- Keyboard toggle (`O`) cycles through stored overlay sequences
- Each toggle steps to the next sequence; within a sequence, states auto-advance by duration

**Overlay as living layer:**
- An overlay state can include its own `field_program` with generators
- The overlay channel renders its own pattern (e.g., slow nebula at 20% opacity)
- UI sprites composite on top of the overlay pattern
- Three visual layers: primary pattern → overlay pattern → UI sprites
- Each layer independently animated, independently sequenced

**Programmed interface evolution:**
```typescript
const interfaceSequence: OverlaySequence = {
  id: 'show-intro',
  name: 'Show Introduction',
  states: [
    // 1. Silence — just the primary pattern
    { overlay: { state: { field_program: { generators: [] } }, blend: { opacity: 0 } },
      duration: 5, transition: { fade_in: 0, fade_out: 0 } },
    // 2. Corner markers fade in
    { overlay: { state: { field_program: { generators: [] }, ui: [corners] },
      blend: { opacity: 0.3, mode: 'over' } },
      duration: 8, transition: { fade_in: 2, fade_out: 0 } },
    // 3. Title reveal
    { overlay: { state: { field_program: { generators: [] }, ui: [corners, titleBanner] },
      blend: { opacity: 0.7, mode: 'screen' } },
      duration: 6, transition: { fade_in: 1.5, fade_out: 1.5 } },
    // 4. Dissolve to clean
    { overlay: { state: { field_program: { generators: [] } }, blend: { opacity: 0 } },
      duration: 3, transition: { fade_in: 0, fade_out: 2 } },
  ],
  loop: false,
}
```

### Phase 8: Preference Learning — The System Develops Taste

**Problem:** The composer wanders randomly within mood ranges. It has no memory of what worked. The operator's ratings go nowhere.

**Fix:** Segment ratings feed back into the composer's behavior. The system develops empirical taste from accumulated sessions.

**Preference model:**
- Segments rated 1 (keep) → their param values become attractors in the mood's ranges
- Segments rated -1 (skip) → their param values become repellers
- Over time, the composer's `pickNext` is biased toward regions that historically produced kept segments

**Implementation path:**
1. Accumulate rated segments per mood
2. Compute weighted param distributions from kept segments
3. `pickNext` samples from empirical distribution (blended with uniform range at configurable ratio)
4. As ratings accumulate, the empirical distribution gains weight
5. New moods can be synthesized from clusters of liked segments — "you seem to like these 40 segments; they form a natural cluster; here's a mood derived from their distribution"

**What changes:**
- `PreferenceModel` class in composer — ingests rated segments, produces biased sampling
- `FlowComposer.pickNext()` accepts optional preference bias
- `MoodConductor` can synthesize new moods from preference clusters
- Archive query: "segments rated 1, grouped by mood" feeds the model

### Phase 9: AI Operator Integration — Natural Language Steering

**Problem:** The AI operator has REST endpoints but no high-level intent interface. Translating "build tension slowly, then release into oceanic calm" into a sequence of FlowSegments requires understanding the param space.

**Fix:** The operator delta path (Phase 5) combined with the vibe map and variant system creates a natural language → visual intent pipeline.

**Intent resolution chain:**
```
"deep ocean drifting into storm"
  → promptToVariant("deep ocean") → 'tide-2'
  → promptToVariant("storm") → 'swirl-3'
  → Compose: [
      { generator: 'tide-2', duration: 20, ease: 'easeInOut',
        params: { speed: 0.6, feedback: 0.5, hueSpeed: 0.04 } },
      { generator: 'swirl-3', duration: 15, ease: 'easeIn',
        params: { speed: 2.5, warp: 1.4, chaos: 0.1, spin: 1.2 } },
    ]
  → Resolve from current state
  → Push to sequencer + archive
```

**What changes:**
- New `POST /operator/intent` endpoint accepting natural language
- Intent parser: splits into phases, resolves each via vibe map + variant system
- Phase durations and easings inferred from language ("slowly" → long duration + easeInOut, "suddenly" → short + easeIn)
- Params selected from variant defaults + mood-appropriate ranges
- AI operator reads `GET /state-summary` for context, `GET /archive/sessions/current` for recent history

**Feedback loop:**
- AI operator sees ratings on its generated segments
- Adjusts future generations based on what the human kept/skipped
- Over time, the AI learns the human's taste for intent interpretation

### Phase 10: Multi-Renderer Sync — True Mirroring

**Problem:** Bridge TUI and web client show different content because they run independent pipelines.

**Fix:** After Phase 4 (client as source of truth), both renderers play the same segments. This phase adds precise synchronization.

**What changes:**
- Bridge tracks playback position (segment index + progress within segment)
- Client receives sync heartbeats: `{ segment_index, progress, timestamp }`
- Client can lock to bridge timing (for multi-display setups)
- New mode: `sync: 'master' | 'slave' | 'independent'`
  - `master`: client generates, bridge follows
  - `slave`: bridge drives, client follows (for pre-recorded shows)
  - `independent`: current behavior (both run their own thing)
